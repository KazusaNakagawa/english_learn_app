# IAM グループ設計と運用手順

このアカウントの IAM グループは CDK（`aws/lib/iam-stack.ts`）で管理されている。
手動で作られたグループは存在しない。

- **どのグループを申請すればよいか** → 「グループ一覧」
- **人を増やす / 減らす** → 「オンボーディング」「オフボーディング」
- **なぜこの構成なのか** → 「設計上の制約」。読まずに変更すると壊れる箇所がある
- 経緯や失敗の記録 → [`aws/iam-group-iac-worklog.md`](aws/iam-group-iac-worklog.md)

> **実機検証: 2026-09-12 に新規ユーザ 1 名（`mfa-test`）で通しに歩いた（[#184](https://github.com/KazusaNakagawa/english_learn_app/issues/184)）。**
> 「オンボーディング」は作成から MFA 登録・アクセスキー発行・MFA セッション取得まで、
> 「オフボーディング」はティアユーザの削除まで到達している。歩いた記録と
> 落ちた箇所は [`aws/iam-group-iac-worklog.md`](aws/iam-group-iac-worklog.md) にある。
>
> **未検証: `admin` のオフボーディング。** 実行者が別の `admin` か root に限られ、
> 平時のメンバーが 0 のため歩けていない。
>
> この Epic では「読んで正しく見えた」が実機で覆った例が複数ある
> （`*-pro` の Deny が AssumeRole セッションで効かなかった、
> グループの重複所属が動いていたプロファイルを壊した、
> オフボーディング手順が zsh で 1 行も実行されずに終わった）。
> 手順が落ちたら、自分の操作より**手順の側が間違っている可能性を先に疑ってよい**。
> 落ちたコマンドとエラー全文を worklog に残すこと。

## グループ一覧

すべてのグループに **MFA ベースライン**（`self-service-credentials` と
`deny-without-mfa`）が付く。下表では省略している。

| グループ | 想定利用者 | 追加ポリシー | できること | できないこと |
| --- | --- | --- | --- | --- |
| `readonly` | 障害・リソース調査をする開発者 | `ReadOnlyAccess`, `deny-secret-reads` | 全リソースの参照 | 一切の変更。秘密の読み取り |
| `audit` | 設定監査 | `SecurityAudit`, `deny-secret-reads` | 設定レベルの監査 | オブジェクトの中身の読み取り |
| `develop` | アプリ開発者 | `develop-workload` | poc / dev への `cdk deploy`、Lambda・API GW の直接操作 | IAM 管理。pro への直接操作 |
| `infra` | アカウント管理者 | `PowerUserAccess`, `infra-administration` | IAM 以外の全操作、ユーザ・グループ運用 | 組織操作。`admin` への自己追加 |
| `billing` | コスト確認 | `AWSBillingReadOnlyAccess` | 請求・Cost Explorer の閲覧 | リソース操作 |
| `admin` | **緊急時のみ**（平時メンバー 0） | `AdministratorAccess` | すべて | — |

### ティアと追加グループ

**グループは自由に組み合わせられない。** 詳細は「設計上の制約」を参照。

| 種別 | グループ | ルール |
| --- | --- | --- |
| ティア | `readonly` / `audit` / `develop` / `infra` / `admin` | **1 人 1 つ**。互いの Deny が衝突する |
| 追加 | `billing` | 任意のティアに重ねられる |

### `ope`（運用監視用）を作らなかった理由

要件段階で候補に挙がったが、**`readonly` と同等になるため作っていない**。
運用担当には `readonly` を割り当て、監視で実際に必要な書き込みが出てきた時点で、
落ちたコマンドを見てから狭いポリシーを足す。

## MFA ベースライン

グループに所属した時点で、**MFA 認証済みセッションでなければ何もできなくなる**。
長期アクセスキーは MFA コンテキストを持たないため、これも拒否される。

```console
$ aws s3 ls --profile dev_user1
An error occurred (AccessDenied) ... with an explicit deny in an
identity-based policy: arn:aws:iam::<account>:policy/deny-without-mfa
```

MFA 未登録の状態でも通るのは、登録を完了するのに必要な操作だけ:

| 対象 | アクション |
| --- | --- |
| 自分自身に限定 | パスワード変更、`iam:GetUser`、仮想 MFA デバイスの作成・有効化・削除・再同期、`iam:ListMFADevices` |
| アカウント全体（絞れない） | `iam:ListVirtualMFADevices`、`iam:GetAccountPasswordPolicy` |
| リソースなし | `sts:GetSessionToken`（これが無いと誰もセッションを取得できない） |

上段は自分以外の ARN を指定すると別途 Deny される。

**下段の 2 つはリソース単位で絞れない**ので、MFA 未登録のユーザでも
アカウント内の仮想 MFA デバイス一覧を列挙できる。
絞ると登録の入口ごと塞がるための妥協で、意図的にそうしてある。

**アクセスキーの作成・ローテーションは含まれない。** MFA セッションが必要。

### コンソールは Deny の理由を隠す

同じ拒否でも、CLI とコンソールで見え方がまったく違う。**先にこれを知らないと、
新規ユーザは MFA ではなく権限の問題だと誤解する**（#184 で実際に起きた）。

CLI はポリシー名まで出す:

```console
$ aws s3 ls --profile mfa-test
An error occurred (AccessDenied) when calling the ListBuckets operation:
User: arn:aws:iam::<account>:user/mfa-test is not authorized to perform:
s3:ListAllMyBuckets with an explicit deny in an identity-based policy:
arn:aws:iam::<account>:policy/deny-without-mfa
```

コンソール（S3 → 汎用バケット）は同じ拒否をこう表示する:

> バケットを一覧表示するアクセス許可がありません
> お客様または AWS 管理者が `s3:ListAllMyBuckets` アクションを許可するように
> アクセス許可を更新してから、このページを更新します。

`deny-without-mfa` の名前はどこにも出ない。文面に従うと「管理者に S3 の権限を
足してもらう」という誤った対処に向かう。**正しい対処は MFA を登録すること。**

原因を切り分けたいときは CloudTrail を見る。IAM のイベントは **us-east-1** に
記録されるので、リージョン指定を忘れないこと:

```bash
aws cloudtrail lookup-events --region us-east-1 \
  --lookup-attributes AttributeKey=Username,AttributeValue=<ユーザ名> \
  --max-results 50
```

### セッションの取得

```bash
AWS_MFA_BASE_PROFILE=<ユーザ名> ./scripts/aws-mfa-session.sh
# → <ユーザ名>-mfa プロファイルが作られる（12 時間有効）
aws sts get-caller-identity --profile <ユーザ名>-mfa
```

セキュリティキー（FIDO/U2F）はコンソールログインには使えるが、
**CLI のセッション取得には使えない**（6 桁の TOTP が必要）。
仮想 MFA デバイスの登録が必須。

## オンボーディング

`infra` の権限で実行する。以降 `--profile infra-user-mfa` は
実行者の MFA セッションプロファイルに読み替える。

```bash
# 1. ユーザ作成
aws iam create-user --user-name alice --profile infra-user-mfa

# 2. コンソールログイン用パスワード（初回変更を強制）
#    create-login-profile はパスワードを返さない。変数に取らずに書くと
#    誰も知らないパスワードが設定され、本人がログインできなくなる。
#    このアカウントはパスワードポリシー未設定（GetAccountPasswordPolicy が
#    NoSuchEntity）なので AWS の既定が効く。rand -base64 24 はそれを満たす。
PW="$(openssl rand -base64 24)"
aws iam create-login-profile \
  --user-name alice \
  --password "$PW" \
  --password-reset-required \
  --profile infra-user-mfa
echo "$PW"   # 安全な経路で本人に渡し、履歴から消すこと

# 3. グループに追加（ティアは 1 つだけ）
aws iam add-user-to-group --user-name alice --group-name readonly --profile infra-user-mfa

# 4. サインイン URL を渡す
echo "https://$(aws sts get-caller-identity --query Account --output text --profile infra-user-mfa).signin.aws.amazon.com/console"
```

本人にやってもらうこと。**順序に意味がある**:

1. コンソールにログインしてパスワードを変更
2. **仮想 MFA デバイスを登録する。デバイス名はユーザ名と完全に一致させる**
   - 経路は 右上のユーザ名 → **セキュリティ認証情報** → 「多要素認証 (MFA)」→
     **MFA デバイスの割り当て** → 「認証アプリケーション」
   - **このページは赤いエラーだらけになるが、それが正常。** `iam:GetLoginProfile`、
     `iam:ListAccessKeys`、`iam:ListUserTags`、`iam:ListSigningCertificates`、
     `iam:GetAccountSummary` などが軒並み `deny-without-mfa` で拒否される。
     MFA の登録操作だけは通るので、そのまま進めてよい
3. **MFA でコンソールにサインインし直してから**アクセスキーを発行する
   （`iam:CreateAccessKey` は MFA 免除リストに入っていないため、
   MFA セッションでないと作れない）
   - キーの発行に成功しても、画面上部に
     `is not authorized to perform: iam:TagUser` という赤いバナーが出る。
     ウィザードの任意項目「説明タグを設定」が失敗しただけで、**キーは作成されている**。
     やり直すとキーが 2 本になり、3 本目は上限で作れなくなるので、
     バナーを見ても再実行しないこと
4. CLI プロファイルを設定する

```bash
aws configure --profile alice     # 3 で発行したキーを入力
```

5. MFA セッションを取得して疎通確認

```bash
AWS_MFA_BASE_PROFILE=alice ./scripts/aws-mfa-session.sh
aws sts get-caller-identity --profile alice-mfa
```

> `AWS_MFA_BASE_PROFILE` に渡すのは **CLI プロファイル名**であって IAM ユーザ名ではない。
> 4 で同じ名前を付けたので一致しているだけ。別名にした場合はプロファイル名の方を渡す。
> 4 を飛ばすと `The config profile (alice) could not be found` で止まる。

> **デバイス名の罠**: `iam:CreateVirtualMFADevice` は `mfa/<デバイス名>` に対して働き、
> ポリシーは `mfa/${aws:username}` に限定している。
> 名前がユーザ名と違うと拒否され、しかもエラーからは理由が分からない。

> **登録に失敗して詰まったら**: そのままウィザードを開き直してよい。
> コンソールが保留中のデバイスを削除してから作り直す（#184 の CloudTrail で確認済み。
> `DeleteVirtualMFADevice` → `CreateVirtualMFADevice` が 1 秒差で走る）。
> これが成立するのは `iam:DeleteVirtualMFADevice` を除外リストに入れてあるためで、
> 無ければ削除が拒否され、同名で作り直せず `EntityAlreadyExists` で詰み、
> `infra` に削除を依頼するしかなくなる。
>
> **人間がデバイスを消す操作は不要**（そもそも保留中のデバイスはコンソールの一覧に
> 出ない。表示されるのは割り当て済みのものだけ）。
>
> **作り直されると QR とシークレットも変わる。** 認証アプリに前回のエントリが
> 残っていると、そこから読んだコードは新しいデバイスと一致せず、何度やっても
> `Authentication code for device is not valid.` になる。**やり直す前にアプリ側の
> エントリを消すこと。** なおこのエラーは「許可が必要です／管理者に依頼してください」
> という見出しの下に表示されるが、**権限の問題ではない**。

## オフボーディング

**IAM はアクセスキーや MFA デバイスが残っているユーザを削除できない**
（`DeleteConflict`）。全員が自分でキーを作れるので、必ず子リソースから消す。

```bash
export AWS_PROFILE=infra-user-mfa   # 実行者の MFA セッションプロファイル
U=alice

# 1. グループから外す（実効権限をまず落とす）
for g in $(aws iam list-groups-for-user --user-name "$U" --query 'Groups[].GroupName' --output text); do
  aws iam remove-user-from-group --user-name "$U" --group-name "$g"
done

# 2. アクセスキー
for k in $(aws iam list-access-keys --user-name "$U" --query 'AccessKeyMetadata[].AccessKeyId' --output text); do
  aws iam delete-access-key --user-name "$U" --access-key-id "$k"
done

# 3. MFA デバイス（無効化してから削除）
for m in $(aws iam list-mfa-devices --user-name "$U" --query 'MFADevices[].SerialNumber' --output text); do
  aws iam deactivate-mfa-device --user-name "$U" --serial-number "$m"
  case "$m" in *:mfa/*) aws iam delete-virtual-mfa-device --serial-number "$m";; esac
done

# 4. コンソールログイン
aws iam delete-login-profile --user-name "$U" 2>/dev/null || true

# 5. 直接アタッチされたポリシー（本来使わないが念のため）
for a in $(aws iam list-attached-user-policies --user-name "$U" --query 'AttachedPolicies[].PolicyArn' --output text); do
  aws iam detach-user-policy --user-name "$U" --policy-arn "$a"
done

# 6. 削除
aws iam delete-user --user-name "$U"
```

> **プロファイルを `--profile` ではなく `AWS_PROFILE` で渡している理由**:
> 以前は `P="--profile infra-user-mfa"` を各行に `$P` で展開していたが、
> **zsh では 1 行も実行されない**。zsh は未クォートの変数を単語分割しないため、
> `--profile infra-user-mfa` が 1 個の引数として渡る:
>
> ```console
> Unknown options: --profile infra-user-mfa
> ```
>
> macOS の既定シェルは zsh なので、そのまま貼ると必ず踏む。しかも手順 1 では
> **コマンド置換の側が落ちる**ためグループ名が 1 つも返らず、ループ本体が
> 0 回実行される。エラーは 1 行しか出ないのに何も外れていない、という終わり方をする。
> #184 で実際に踏んだ。

> **手順 3 の順序は崩せない。** 無効化を飛ばして削除すると弾かれる:
>
> ```console
> An error occurred (DeleteConflict) when calling the DeleteVirtualMFADevice
> operation: MFA VirtualDevice in use. Must deactivate first.
> ```

**急ぎで権限だけ止めたい場合**は 1 と 2 だけでよい。削除は後からできる。

上の手順は `infra` で実行できる**ティア 5 グループ（`readonly` / `audit` /
`develop` / `infra` / `billing`）のユーザ専用**。`admin` に属するユーザには
そのまま使えない。

### break-glass（`admin`）ユーザのオフボーディング

**`admin` からの削除は `infra` ではできない。** `iam:RemoveUserFromGroup` の
スコープは上記 5 グループに限定してあり、`admin` は自己昇格を防ぐため
意図的に除外されている（[設計上の制約 2](#2-admin-は専用ユーザにしか効かない)）。

> **この手順だけ実機で歩けていない。** 実行者が別の `admin` か root に限られ、
> 平時のメンバーが 0 のため #184 の検証対象から外れた。ポリシーを読んで書いたもの。

実行者は**別の `admin` ユーザか root** になる。平時の `admin` はメンバー 0 なので、
ふつうは root でコンソールから行う（root のアクセスキーは作らない）。
CLI で行う場合、手順そのものは同じで `AWS_PROFILE` だけ差し替える:

```bash
export AWS_PROFILE=<その admin の CLI プロファイル名>-mfa   # infra-user-mfa では手順 1 が通らない
U=break-glass-bob
```

> **`-mfa` が付くのは CLI プロファイル名であって IAM ユーザ名ではない。**
> `aws-mfa-session.sh` は `AWS_MFA_BASE_PROFILE` に渡された**プロファイル名**に
> `-mfa` を付けてセッションを書き出す（[オンボーディング](#オンボーディング)の
> 手順 4 と同じ話）。`aws configure` でユーザ名と同じ名前を付けていれば一致するが、
> 別名にしていると存在しないプロファイルを指し、手順 1 の前に落ちる:
>
> ```console
> The config profile (break-glass-bob-mfa) could not be found
> ```
>
> 分からなければ `aws configure list-profiles` で確認すること。

`AWS_PROFILE` を `infra-user-mfa` のまま実行すると、手順 1 は `admin` の行だけが
`AccessDenied` で落ちる。ループに `set -e` を付けていないので処理は先に進み、
**手順 6 が「`admin` に所属したまま」で失敗する**。
前書きで説明している `DeleteConflict`（キー / MFA デバイス）とは原因が違うので、
エラー文をよく読むこと。

## デプロイ

IAM はアカウントグローバルなので、**`VoicevoxStack-{env}` と違い環境サフィックスが無い**。
`IamStack` は 1 つだけ存在する。

```bash
cd aws
npm run diff:iam -- --profile <ユーザ名>-mfa      # 必ず先に差分を見る
npm run deploy:iam -- --profile <ユーザ名>-mfa
```

`bin/iam-app.ts` という専用のエントリを使っている。#171 の時点では
`bin/app.ts` に相乗りさせると `VOICEVOX_API_KEY_*` 未設定で失敗したためだが、
その依存は #182 で解消した（秘密は Secrets Manager から実行時に読む）。
それでもエントリを分けたままにしているのは、IAM の変更は誤ると
アカウントから締め出される一方で、レビューとデプロイの頻度が
アプリ側のスタックとまったく違うため。

環境ごとの分離はアカウント境界ではなく**ポリシー内の ARN 条件**で行っている
（poc / dev / pro が同一アカウントに同居しているため）。

## 設計上の制約

変更前に読むこと。ここを知らずに触ると、静かに壊れる。

### 1. Deny はグループではなくユーザに効く

あるグループのポリシーに書いた Deny は、**そのユーザが所属する他の全グループの
Allow を打ち消す**。つまりグループポリシーの Deny は、事実上そのユーザにとって
アカウント全体の Deny になる。

**Deny に書いてよいのは「どのグループも与えるべきでないもの」だけ。**
「このグループには不要」程度のものを Deny すると、必ず組み合わせで壊れる。

この Epic では同じ過ちを 3 回踏んだ:

| Deny した対象 | 巻き込んだもの |
| --- | --- |
| `iam:*` | MFA ベースライン（全員が MFA 登録不能に） |
| `account:*` / `ce:*` / `aws-portal:*` | `billing` |
| `organizations:*` | `SecurityAudit` の組織読み取り |

ワイルドカードの Deny は書いた瞬間は簡潔で正しく見えるが、
**そのサービスの読み取りを必要とする他グループを巻き込む**。
`aws/test/admin-tier-groups.test.ts` に不変条件テストを置いてある。

### 2. `admin` は専用ユーザにしか効かない

**既存の開発者を `admin` に追加しても管理者にならない。**
その人が `develop` や `infra` にも属していれば、そちらの Deny が
`AdministratorAccess` を上書きする。

しかも**それが発覚するのは緊急時**。break-glass 用には
**他のどのグループにも属さない専用ユーザ**を作ること。

### 3. `infra` は実質的に管理者に近い

`infra` は `iam:CreateRole` と `iam:AttachRolePolicy` を持つため、
自分を信頼するロールを作って `AdministratorAccess` を付け、assume できる。
**assume 後は呼び出し元の identity policy が評価されない**ので、
`infra` にかけた Deny はすべて回避できる。

これは Permissions Boundary で縛る道もあったが、**維持コストが目的に見合わない**と判断して
許容している。したがって `infra` と `admin` の差は
**防止ではなく CloudTrail での可視性**である。

ただし一撃で届く経路は塞いである:

- `admin` グループへの自己追加
- `AdministratorAccess` の直接アタッチ
- このスタックのポリシー自体の書き換え（MFA ベースラインの無効化）

### 4. pro の保護はスタック側で行う

`develop` に `*-pro` の Deny を書いても **`cdk deploy` は止まらない**。
CDK は bootstrap ロールを assume して動くため（上と同じ理由）、
しかも bootstrap ロールはアカウント + リージョン単位で poc/dev/pro 共通。

そのため `pro` はスタック側で 2 段に守る。

| 保護 | 止まるもの | 置き場所 |
| --- | --- | --- |
| 削除保護 (`terminationProtection`) | スタックの削除 | `aws/lib/voicevox-stack.ts`（#174） |
| スタックポリシー | 既存リソースの**置換と削除** | `aws/stack-policies/voicevox-pro.json`（#186） |

削除保護だけでは足りない。止まるのは削除で、**更新は止まらない**ため、
誤った `deploy:pro` が Lambda や API Gateway を置換する経路が残る。

identity policy 側の `*-pro` Deny は、**ユーザ自身の credential で直接叩く場合にのみ**効く。

スタックポリシーは CDK から設定できない（`cdk.StackProps` に `stackPolicy` が無く、
L1 コンストラクトも無い）。CloudFormation の `SetStackPolicy` を別に呼ぶ必要があるので、
文書をリポジトリに置き、`npm run deploy:pro` の `postdeploy:pro` フック
（[`scripts/apply-stack-policy.sh`](../scripts/apply-stack-policy.sh)）で毎回適用する。
スタックポリシーは更新では消えないが、**スタックを作り直すと消える**ためで、
「覚えておく」に任せない。

```bash
# 通常はデプロイに付いてくる
AWS_PROFILE=infra-user-mfa npm run deploy:pro

# 手で適用する / 現在の内容を確認する
aws cloudformation set-stack-policy \
  --stack-name VoicevoxStack-pro \
  --stack-policy-body file://aws/stack-policies/voicevox-pro.json

aws cloudformation get-stack-policy --stack-name VoicevoxStack-pro \
  --query StackPolicyBody --output text
```

> **プロファイルは `AWS_PROFILE` で渡すこと。**
> `npm run deploy:pro -- --profile x` の `--profile` は `cdk deploy` にしか渡らず、
> `postdeploy:pro` フックは既定のプロファイルで動いてしまう
> （スタックが見えず、デプロイ成功の直後にフックだけが失敗する）。

**スタックポリシーは deny-by-default。** 1 本でもアタッチすると、
既存リソースへの更新は明示的に Allow したものしか通らない。
`voicevox-pro.json` の Allow（`Update:Modify`）が保護の要で、
ここを `Update:*` に広げると `Update:Replace` / `Update:Delete` まで含むため
**保護が黙って消える**。新規リソースの追加は常に許可される（ポリシーの対象外）。

> **現状: 文書とフックは用意済みだが、まだアタッチされていない。**
> `VoicevoxStack-pro` が一度もデプロイされていないため。初回 `deploy:pro` の
> 直後にフックが適用し、読み戻して一致を確認する。

#### 意図的に置換・削除を伴う変更をするとき

ポリシーを外すのではなく、その 1 回だけ緩める。CDK 経由の場合はこうする。

```bash
cat > /tmp/allow-once.json <<'JSON'
{ "Statement": [ { "Effect": "Allow", "Action": "Update:*", "Principal": "*", "Resource": "*" } ] }
JSON

aws cloudformation set-stack-policy \
  --stack-name VoicevoxStack-pro \
  --stack-policy-body file:///tmp/allow-once.json

AWS_PROFILE=infra-user-mfa npm run deploy:pro   # 完了後、フックが厳しい側に戻す
```

CloudFormation を直接叩くなら、その更新のあいだだけ効くポリシーを渡せる。
保存されているポリシー自体は変わらないので戻し忘れが起きない。

```bash
aws cloudformation update-stack \
  --stack-name VoicevoxStack-pro \
  --use-previous-template \
  --stack-policy-during-update-body file:///tmp/allow-once.json
```

`cdk deploy` に `--stack-policy-during-update-body` を渡す方法は無いため、
CDK を使う限り上の「一時的に緩めて、フックで戻す」が実際の手順になる。

**この上書きが頻繁に必要になったら、ポリシーを捨てるのではなく deny の粒度を見直す。**
`Resource` をリソース単位（`LogicalResourceId/...`）に絞れば、
置換されても困らないものは通せる。

### 5. 名前でスコープできないリソースがある

| サービス | 理由 |
| --- | --- |
| API Gateway v2 | ARN が生成 ID 形式で、名前も環境も含まない |
| CloudWatch アラーム | CDK 生成のサフィックスが付く |

この 2 つは `develop` に対してアカウント全体（pro を含む）で許可されている。
**環境分離に実在する穴**として認識しておくこと。

### 6. IAM の変更は即時に反映されない

ポリシーやメンバーシップの変更は数秒から十数秒遅れる。
実測では、付与直後 5 秒では効かず 10 秒で反映された。
自動化するならリトライ前提で書くこと。
