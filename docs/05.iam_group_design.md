# IAM グループ設計と運用手順

このアカウントの IAM グループは CDK（`aws/lib/iam-stack.ts`）で管理されている。
手動で作られたグループは存在しない。

- **どのグループを申請すればよいか** → 「グループ一覧」
- **人を増やす / 減らす** → 「オンボーディング」「オフボーディング」
- **なぜこの構成なのか** → 「設計上の制約」。読まずに変更すると壊れる箇所がある
- 経緯や失敗の記録 → [`aws/iam-group-iac-worklog.md`](aws/iam-group-iac-worklog.md)

---

## グループ一覧

すべてのグループに **MFA ベースライン**（`self-service-credentials` と
`deny-without-mfa`）が付く。下表では省略している。

| グループ | 想定利用者 | 追加ポリシー | できること | できないこと |
| --- | --- | --- | --- | --- |
| `readonly` | 障害・リソース調査をする開発者 | `ReadOnlyAccess`, `deny-secret-reads` | 全リソースの参照 | 一切の変更。秘密の読み取り |
| `audit` | 設定監査 | `SecurityAudit`, `deny-secret-reads` | 設定レベルの監査 | オブジェクトの中身の読み取り |
| `develop` | アプリ開発者 | `develop-workload` | poc / dev への `cdk deploy`、Lambda・API GW の直接操作 | IAM 管理。pro への直接操作 |
| `infra` | アカウント管理者 | `PowerUserAccess`, `infra-administration` | IAM 以外の全操作、ユーザ・グループ運用 | 組織操作。`admin` への自己追加 |
| `billing` | コスト確認 | `AWSBillingReadOnlyAccess` | 請求・Cost Explorer の閲覧 | リソース操作 |
| `admin` | **緊急時のみ**（平時メンバー 0） | `AdministratorAccess` | すべて | — |

### ティアと追加グループ

**グループは自由に組み合わせられない。** 詳細は「設計上の制約」を参照。

| 種別 | グループ | ルール |
| --- | --- | --- |
| ティア | `readonly` / `audit` / `develop` / `infra` / `admin` | **1 人 1 つ**。互いの Deny が衝突する |
| 追加 | `billing` | 任意のティアに重ねられる |

### `ope`（運用監視用）を作らなかった理由

要件段階で候補に挙がったが、**`readonly` と同等になるため作っていない**。
運用担当には `readonly` を割り当て、監視で実際に必要な書き込みが出てきた時点で、
落ちたコマンドを見てから狭いポリシーを足す。

## MFA ベースライン

グループに所属した時点で、**MFA 認証済みセッションでなければ何もできなくなる**。
長期アクセスキーは MFA コンテキストを持たないため、これも拒否される。

```console
$ aws s3 ls --profile dev_user1
An error occurred (AccessDenied) ... with an explicit deny in an
identity-based policy: arn:aws:iam::<account>:policy/deny-without-mfa
```

MFA 未登録の状態でも通るのは、登録を完了するのに必要な操作だけ:

| 対象 | アクション |
| --- | --- |
| 自分自身に限定 | パスワード変更、`iam:GetUser`、仮想 MFA デバイスの作成・有効化・削除・再同期、`iam:ListMFADevices` |
| アカウント全体（絞れない） | `iam:ListVirtualMFADevices`、`iam:GetAccountPasswordPolicy` |
| リソースなし | `sts:GetSessionToken`（これが無いと誰もセッションを取得できない） |

上段は自分以外の ARN を指定すると別途 Deny される。

**下段の 2 つはリソース単位で絞れない**ので、MFA 未登録のユーザでも
アカウント内の仮想 MFA デバイス一覧を列挙できる。
絞ると登録の入口ごと塞がるための妥協で、意図的にそうしてある。

**アクセスキーの作成・ローテーションは含まれない。** MFA セッションが必要。

### セッションの取得

```bash
AWS_MFA_BASE_PROFILE=<ユーザ名> ./scripts/aws-mfa-session.sh
# → <ユーザ名>-mfa プロファイルが作られる（12 時間有効）
aws sts get-caller-identity --profile <ユーザ名>-mfa
```

セキュリティキー（FIDO/U2F）はコンソールログインには使えるが、
**CLI のセッション取得には使えない**（6 桁の TOTP が必要）。
仮想 MFA デバイスの登録が必須。

## オンボーディング

`infra` の権限で実行する。以降 `--profile infra-user-mfa` は
実行者の MFA セッションプロファイルに読み替える。

```bash
# 1. ユーザ作成
aws iam create-user --user-name alice --profile infra-user-mfa

# 2. コンソールログイン用パスワード（初回変更を強制）
#    create-login-profile はパスワードを返さない。変数に取らずに書くと
#    誰も知らないパスワードが設定され、本人がログインできなくなる。
PW="$(openssl rand -base64 24)"
aws iam create-login-profile \
  --user-name alice \
  --password "$PW" \
  --password-reset-required \
  --profile infra-user-mfa
echo "$PW"   # 安全な経路で本人に渡し、履歴から消すこと

# 3. グループに追加（ティアは 1 つだけ）
aws iam add-user-to-group --user-name alice --group-name readonly --profile infra-user-mfa

# 4. サインイン URL を渡す
echo "https://$(aws sts get-caller-identity --query Account --output text --profile infra-user-mfa).signin.aws.amazon.com/console"
```

本人にやってもらうこと。**順序に意味がある**:

1. コンソールにログインしてパスワードを変更
2. **仮想 MFA デバイスを登録する。デバイス名はユーザ名と完全に一致させる**
3. **MFA でコンソールにサインインし直してから**アクセスキーを発行する
   （`iam:CreateAccessKey` は MFA 免除リストに入っていないため、
   MFA セッションでないと作れない）
4. CLI プロファイルを設定する

```bash
aws configure --profile alice     # 3 で発行したキーを入力
```

5. MFA セッションを取得して疎通確認

```bash
AWS_MFA_BASE_PROFILE=alice ./scripts/aws-mfa-session.sh
aws sts get-caller-identity --profile alice-mfa
```

> `AWS_MFA_BASE_PROFILE` に渡すのは **CLI プロファイル名**であって IAM ユーザ名ではない。
> 4 で同じ名前を付けたので一致しているだけ。別名にした場合はプロファイル名の方を渡す。
> 4 を飛ばすと `The config profile (alice) could not be found` で止まる。

> **デバイス名の罠**: `iam:CreateVirtualMFADevice` は `mfa/<デバイス名>` に対して働き、
> ポリシーは `mfa/${aws:username}` に限定している。
> 名前がユーザ名と違うと拒否され、しかもエラーからは理由が分からない。

> **登録に失敗して詰まったら**: 作りかけのデバイスは MFA 未登録の状態でも削除できる
> （`iam:DeleteVirtualMFADevice` を除外リストに入れてある）。
> 同名で作り直す前に削除すること。削除せずに再作成すると `EntityAlreadyExists` になる。

## オフボーディング

**IAM はアクセスキーや MFA デバイスが残っているユーザを削除できない**
（`DeleteConflict`）。全員が自分でキーを作れるので、必ず子リソースから消す。

```bash
U=alice
P="--profile infra-user-mfa"

# 1. グループから外す（実効権限をまず落とす）
for g in $(aws iam list-groups-for-user --user-name "$U" --query 'Groups[].GroupName' --output text $P); do
  aws iam remove-user-from-group --user-name "$U" --group-name "$g" $P
done

# 2. アクセスキー
for k in $(aws iam list-access-keys --user-name "$U" --query 'AccessKeyMetadata[].AccessKeyId' --output text $P); do
  aws iam delete-access-key --user-name "$U" --access-key-id "$k" $P
done

# 3. MFA デバイス（無効化してから削除）
for m in $(aws iam list-mfa-devices --user-name "$U" --query 'MFADevices[].SerialNumber' --output text $P); do
  aws iam deactivate-mfa-device --user-name "$U" --serial-number "$m" $P
  case "$m" in *:mfa/*) aws iam delete-virtual-mfa-device --serial-number "$m" $P;; esac
done

# 4. コンソールログイン
aws iam delete-login-profile --user-name "$U" $P 2>/dev/null || true

# 5. 直接アタッチされたポリシー（本来使わないが念のため）
for a in $(aws iam list-attached-user-policies --user-name "$U" --query 'AttachedPolicies[].PolicyArn' --output text $P); do
  aws iam detach-user-policy --user-name "$U" --policy-arn "$a" $P
done

# 6. 削除
aws iam delete-user --user-name "$U" $P
```

**急ぎで権限だけ止めたい場合**は 1 と 2 だけでよい。削除は後からできる。

> **`admin` からは `infra` では外せない。** `iam:RemoveUserFromGroup` は
> `readonly` / `audit` / `develop` / `infra` / `billing` にスコープしてあり、
> `admin` は意図的に除外されている（自己昇格を防ぐため）。
> break-glass 用の専用ユーザを削除するときは `admin` か root で実行すること。
>
> 上のループは `set -e` を付けていないので、`admin` の行だけ `AccessDenied` で
> 素通りし、**手順 6 が「グループに所属したまま」で失敗する**。
> 前書きで説明している `DeleteConflict`（キー / MFA デバイス）とは別の原因なので、
> エラー文をよく読むこと。

## デプロイ

IAM はアカウントグローバルなので、**`VoicevoxStack-{env}` と違い環境サフィックスが無い**。
`IamStack` は 1 つだけ存在する。

```bash
cd aws
npm run diff:iam -- --profile <ユーザ名>-mfa      # 必ず先に差分を見る
npm run deploy:iam -- --profile <ユーザ名>-mfa
```

`bin/iam-app.ts` という専用のエントリを使っており、**VOICEVOX の API キーを必要としない**。
`bin/app.ts` に相乗りさせると、CDK がセレクタ適用前に全スタックを構築する都合で
`VOICEVOX_API_KEY_*` が無いと失敗する。

環境ごとの分離はアカウント境界ではなく**ポリシー内の ARN 条件**で行っている
（poc / dev / pro が同一アカウントに同居しているため）。

## 設計上の制約

変更前に読むこと。ここを知らずに触ると、静かに壊れる。

### 1. Deny はグループではなくユーザに効く

あるグループのポリシーに書いた Deny は、**そのユーザが所属する他の全グループの
Allow を打ち消す**。つまりグループポリシーの Deny は、事実上そのユーザにとって
アカウント全体の Deny になる。

**Deny に書いてよいのは「どのグループも与えるべきでないもの」だけ。**
「このグループには不要」程度のものを Deny すると、必ず組み合わせで壊れる。

この Epic では同じ過ちを 3 回踏んだ:

| Deny した対象 | 巻き込んだもの |
| --- | --- |
| `iam:*` | MFA ベースライン（全員が MFA 登録不能に） |
| `account:*` / `ce:*` / `aws-portal:*` | `billing` |
| `organizations:*` | `SecurityAudit` の組織読み取り |

ワイルドカードの Deny は書いた瞬間は簡潔で正しく見えるが、
**そのサービスの読み取りを必要とする他グループを巻き込む**。
`aws/test/admin-tier-groups.test.ts` に不変条件テストを置いてある。

### 2. `admin` は専用ユーザにしか効かない

**既存の開発者を `admin` に追加しても管理者にならない。**
その人が `develop` や `infra` にも属していれば、そちらの Deny が
`AdministratorAccess` を上書きする。

しかも**それが発覚するのは緊急時**。break-glass 用には
**他のどのグループにも属さない専用ユーザ**を作ること。

### 3. `infra` は実質的に管理者に近い

`infra` は `iam:CreateRole` と `iam:AttachRolePolicy` を持つため、
自分を信頼するロールを作って `AdministratorAccess` を付け、assume できる。
**assume 後は呼び出し元の identity policy が評価されない**ので、
`infra` にかけた Deny はすべて回避できる。

これは Permissions Boundary で縛る道もあったが、**維持コストが目的に見合わない**と判断して
許容している。したがって `infra` と `admin` の差は
**防止ではなく CloudTrail での可視性**である。

ただし一撃で届く経路は塞いである:

- `admin` グループへの自己追加
- `AdministratorAccess` の直接アタッチ
- このスタックのポリシー自体の書き換え（MFA ベースラインの無効化）

### 4. pro の保護はスタック側で行う

`develop` に `*-pro` の Deny を書いても **`cdk deploy` は止まらない**。
CDK は bootstrap ロールを assume して動くため（上と同じ理由）、
しかも bootstrap ロールはアカウント + リージョン単位で poc/dev/pro 共通。

そのため `VoicevoxStack` の `pro` には**削除保護**を入れている。
更新を止めるスタックポリシーは未適用（`VoicevoxStack-pro` が未デプロイのため）。

identity policy 側の `*-pro` Deny は、**ユーザ自身の credential で直接叩く場合にのみ**効く。

### 5. 名前でスコープできないリソースがある

| サービス | 理由 |
| --- | --- |
| API Gateway v2 | ARN が生成 ID 形式で、名前も環境も含まない |
| CloudWatch アラーム | CDK 生成のサフィックスが付く |

この 2 つは `develop` に対してアカウント全体（pro を含む）で許可されている。
**環境分離に実在する穴**として認識しておくこと。

### 6. IAM の変更は即時に反映されない

ポリシーやメンバーシップの変更は数秒から十数秒遅れる。
実測では、付与直後 5 秒では効かず 10 秒で反映された。
自動化するならリトライ前提で書くこと。
